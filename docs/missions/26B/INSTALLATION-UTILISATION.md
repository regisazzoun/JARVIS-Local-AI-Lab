# Installation et utilisation

Installateur : `sudo /opt/jarvis/conversation/.venv/bin/python agentic/mission_engine26b/install.py`. Il compile les sources avant copie, refuse une mission en cours, sauvegarde les anciens modules sous `/var/backups/jarvis/mission-engine26b/`, contrôle que la politique hôte reste identique et ne redémarre que jarvis-conversation. Les bases, broker et services LiveKit ne sont pas remplacés. Empreintes et sauvegardes : [INSTALLATIONS.json](INSTALLATIONS.json).

Les nouveaux objectifs autonomes soumis au moteur utilisent `spec.assurance=true` par défaut ; les specs historiques ne sont pas modifiées. L’API reçoit un objectif brut, sans tableau tasks. JARVIS utilise le même mission_plan qu’en26 ; l’extraction et le contrôle de couverture sont automatiques. Le retour contient version courante, coverage et execution_allowed. Un FAIL demande au modèle sa propre révision append/patch ; il n’autorise pas les opérations.

mission_progress expose les exigences extraites, plans, audits, catalogue de preuves et exemples actifs `26b.7`. plan_version permet une relecture complète d’une ancienne version ; la vue courante évite de recopier toutes les anciennes définitions dans chaque inférence. L’interface décode les tableaux/objets envoyés comme chaînes JSON valides, puis les valide sans transformer les types scalaires. Le décodeur reconnaît aussi les champs contigus mal répartis par le parseur natif, sans conflit ni invention de données, et répare uniquement l’échappement apostrophe invalide après échec JSON strict. Les diagnostics de schéma indiquent le champ concerné et les variantes exigées. Les versions ne s’incrémentent pas pour un schéma refusé ; un candidat valide mais incomplet est conservé avec audit FAIL et exécution suspendue.

Les rapports restent en prose libre. mission_report_review reçoit content et scope task/mission pour une prélecture ; les outils de réception/publication l’imposent aussi. Le modèle doit reprendre lui-même son texte depuis les faits contradictoires/manquants. Chaque tentative de texte reste dans narrative_review. Le contrôleur classe des passages exacts et cite uniquement des références autorisées ; ses propres erreurs de format sont journalisées séparément dans review_format_rejected et ne sont pas imputées au rédacteur. Les références attendues sont des ids d’invocation, event:N, plan:N ou task:id réellement présents dans le journal.

Les contrats de lecture sont explicites : source={tool:host_read_file,arguments:{path:chemin}}. JSON utilise des JSON Pointers (/count), dont la chaîne vide pour la racine, et peut déclarer relations:[{kind:length,array:/names,count:/count}] pour vérifier le total réel de la liste ; text utilise le contenu exact equals ou son SHA256 ; service observe seulement l’état systemd réel. Le nouveau kind digest relit un manifeste JSON et son fichier cible baseline_source, puis compare le champ /sha256 à l’empreinte réelle. Il ne requiert ni empreinte devinée ni commande fournie par Codex. Un rapport libre utilise kind report, source pointant sur son fichier ; la revue vérifie le texte sans empreinte préétablie. Un résultat indisponible conserve INSUFFICIENT et ne reçoit pas la tâche.

Pour le cas partiel : conserver le rapport reçu par mission_report_review, puis mission_block avec une preuve réelle et le rapport local. L’exécution attend alors la dépendance externe ; ce n’est pas une clôture technique réussie.

## Corrections du contrôleur pendant les essais

La couverture est prospective : les sorties prévues ne doivent pas déjà exister pour autoriser leur production. Le contrôleur ne reçoit plus les reçus d’exécution dans cette revue et distingue les autorisations du propriétaire des permissions Unix ; les anciennes conclusions erronées restent au journal. Le contrat d’extraction des objectifs reste `26b.4`, indépendamment du contrat de revue `26b.7`. Un prédicat report doit viser le rapport de la tâche ou un artefact de prose déclaré, jamais le programme source ou un journal brut. Une ancienne liaison invalide peut être réparée par le modèle, sans retirer une condition métier déjà prouvée. Les références originales du broker restent disponibles même pour un reçu long abrégé. La réponse de prélecture est compacte par défaut ; `include_evidence=true` permet la vue complète, conservée dans tous les cas dans le journal.

Les inférences de contrôle utilisent désormais `format` avec le schéma JSON actif et aucun outil d’action, pour contraindre les identifiants et types pendant la génération. La validation locale reste obligatoire. Ce mécanisme suit le [contrat de sorties structurées Ollama](https://github.com/ollama/ollama/blob/main/docs/capabilities/structured-outputs.mdx). Le test réel de transport est conservé dans STRUCTURED-OUTPUT-PROBE.json ; il ne démontre ni la justesse sémantique d’une revue ni l’autonomie opérationnelle. mission_evidence permet également de relire un event:N de la mission courante, sans accepter un événement d’une autre mission ni en faire une invocation technique pour la réception.

## Dépendances et portée des affirmations — contrat26b.6

Un contrôle déterministe compare les chemins absolus observés dans les prédicats, notamment la cible déclarée d’un manifeste, aux producteurs d’artefacts du plan. Un lecteur doit suivre tous les producteurs déclarés de sa cible ; la vérification intermédiaire du producteur lui-même reste possible. Cela signale le risque réel d’un manifeste produit avant une réécriture de son inventaire, sans écrire les nouvelles dépendances à la place du modèle. Ce contrôle porte sur les contrats déclarés, pas sur une interprétation universelle des effets d’un programme. Une attente externe globale refuse également d’abandonner des tâches locales encore exécutables indépendamment ; les descendants impossibles de la tâche bloquée ne constituent pas un faux obstacle à l’attente.

Pour une revue de prose, le moteur fournit les définitions originales du plan courant et des versions citées, avec leurs empreintes. Un récit fidèle d’un état incorrect peut être étayé sans constituer une réussite technique. Une intention explicitement future se contrôle contre le plan ; elle ne devient pas une action reçue. Les anciens avis de couverture restent au journal mais ne sont plus présentés au contrôleur prospectif comme des exigences, pour limiter la répétition de ses erreurs antérieures.

Le contrôle de couverture d’une liste explicitement exacte exige un prédicat de contenu exact ou une conservation comparée de ce même tableau avec une source indépendante. Le seul type array et sa longueur ne prouvent pas ses membres ; la conservation d’un champ sans rapport ou une comparaison du fichier avec lui-même ne couvrent pas cette exigence. Les noms de propriétés et valeurs restent choisis par JARVIS.
