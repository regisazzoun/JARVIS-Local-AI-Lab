# Installation et utilisation

Installateur : `sudo /opt/jarvis/conversation/.venv/bin/python agentic/mission_engine26b/install.py`. Il compile les sources avant copie, refuse une mission en cours, sauvegarde les anciens modules sous `/var/backups/jarvis/mission-engine26b/`, contrôle que la politique hôte reste identique et ne redémarre que jarvis-conversation. Les bases, broker et services LiveKit ne sont pas remplacés. Empreintes et sauvegardes : [INSTALLATIONS.json](INSTALLATIONS.json).

Les nouveaux objectifs autonomes soumis au moteur utilisent `spec.assurance=true` par défaut ; les specs historiques ne sont pas modifiées. L’API reçoit un objectif brut, sans tableau tasks. JARVIS utilise le même mission_plan qu’en26 ; l’extraction et le contrôle de couverture sont automatiques. Le retour contient version courante, coverage et execution_allowed. Un FAIL demande au modèle sa propre révision append/patch ; il n’autorise pas les opérations.

mission_progress expose les exigences extraites, plans, audits, catalogue de preuves et exemples actifs `26b.9`. plan_version permet une relecture complète d’une ancienne version ; la vue courante évite de recopier toutes les anciennes définitions dans chaque inférence. L’interface décode les tableaux/objets envoyés comme chaînes JSON valides, puis les valide sans transformer les types scalaires. Le décodeur reconnaît aussi les champs contigus mal répartis par le parseur natif, sans conflit ni invention de données, et répare uniquement l’échappement apostrophe invalide après échec JSON strict. Les diagnostics de schéma indiquent le champ concerné et les variantes exigées. Les versions ne s’incrémentent pas pour un schéma refusé ; un candidat valide mais incomplet est conservé avec audit FAIL et exécution suspendue.

Les rapports restent en prose libre. mission_report_review reçoit content et scope task/mission pour une prélecture ; les outils de réception/publication l’imposent aussi. Le modèle doit reprendre lui-même son texte depuis les faits contradictoires/manquants. Chaque tentative de texte reste dans narrative_review. Le contrôleur classe des passages exacts et cite uniquement des références autorisées ; ses propres erreurs de format sont journalisées séparément dans review_format_rejected et ne sont pas imputées au rédacteur. Les références attendues sont des ids d’invocation, event:N, plan:N ou task:id réellement présents dans le journal.

Les contrats de lecture sont explicites : source={tool:host_read_file,arguments:{path:chemin}}. JSON utilise des JSON Pointers (/count), dont la chaîne vide pour la racine, et peut déclarer relations:[{kind:length,array:/names,count:/count}] pour vérifier le total réel de la liste ; text utilise le contenu exact equals ou son SHA256 ; service observe seulement l’état systemd réel. Le nouveau kind digest relit un manifeste JSON et son fichier cible baseline_source, puis compare le champ /sha256 à l’empreinte réelle. Il ne requiert ni empreinte devinée ni commande fournie par Codex. Un rapport libre utilise kind report, source pointant sur son fichier ; la revue vérifie le texte sans empreinte préétablie. Un résultat indisponible conserve INSUFFICIENT et ne reçoit pas la tâche.

Pour le cas partiel : conserver le rapport reçu par mission_report_review, puis mission_block avec une preuve réelle et le rapport local. L’exécution attend alors la dépendance externe ; ce n’est pas une clôture technique réussie.

## Corrections du contrôleur pendant les essais

La couverture est prospective : les sorties prévues ne doivent pas déjà exister pour autoriser leur production. Le contrôleur ne reçoit plus les reçus d’exécution dans cette revue et distingue les autorisations du propriétaire des permissions Unix ; les anciennes conclusions erronées restent au journal. Le contrat d’extraction des objectifs reste `26b.4`, indépendamment du contrat de revue `26b.9`. Un prédicat report doit viser le rapport de la tâche ou un artefact de prose déclaré, jamais le programme source ou un journal brut. Une ancienne liaison invalide peut être réparée par le modèle, sans retirer une condition métier déjà prouvée. Les références originales du broker restent disponibles même pour un reçu long abrégé. La réponse de prélecture est compacte par défaut ; `include_evidence=true` permet la vue complète, conservée dans tous les cas dans le journal.

Les inférences de contrôle utilisent désormais `format` avec le schéma JSON actif et aucun outil d’action, pour contraindre les identifiants et types pendant la génération. La validation locale reste obligatoire. Ce mécanisme suit le [contrat de sorties structurées Ollama](https://github.com/ollama/ollama/blob/main/docs/capabilities/structured-outputs.mdx). Le test réel de transport est conservé dans STRUCTURED-OUTPUT-PROBE.json ; il ne démontre ni la justesse sémantique d’une revue ni l’autonomie opérationnelle. mission_evidence permet également de relire un event:N de la mission courante, sans accepter un événement d’une autre mission ni en faire une invocation technique pour la réception.

## Dépendances et portée des affirmations — contrat26b.6

Un contrôle déterministe compare les chemins absolus observés dans les prédicats, notamment la cible déclarée d’un manifeste, aux producteurs d’artefacts du plan. Un lecteur doit suivre tous les producteurs déclarés de sa cible ; la vérification intermédiaire du producteur lui-même reste possible. Cela signale le risque réel d’un manifeste produit avant une réécriture de son inventaire, sans écrire les nouvelles dépendances à la place du modèle. Ce contrôle porte sur les contrats déclarés, pas sur une interprétation universelle des effets d’un programme. Une attente externe globale refuse également d’abandonner des tâches locales encore exécutables indépendamment ; les descendants impossibles de la tâche bloquée ne constituent pas un faux obstacle à l’attente.

Pour une revue de prose, le moteur fournit les définitions originales du plan courant et des versions citées, avec leurs empreintes. Un récit fidèle d’un état incorrect peut être étayé sans constituer une réussite technique. Une intention explicitement future se contrôle contre le plan ; elle ne devient pas une action reçue. Les anciens avis de couverture restent au journal mais ne sont plus présentés au contrôleur prospectif comme des exigences, pour limiter la répétition de ses erreurs antérieures.

Le contrôle de couverture d’une liste explicitement exacte exige un prédicat de contenu exact ou une conservation comparée de ce même tableau avec une source indépendante. Le seul type array et sa longueur ne prouvent pas ses membres ; la conservation d’un champ sans rapport ou une comparaison du fichier avec lui-même ne couvrent pas cette exigence. Les noms de propriétés et valeurs restent choisis par JARVIS.

La sortie structurée du contrôle de couverture exige désormais un objet avec une clé obligatoire par exigence R1, R2, etc. Les clés manquantes sont un défaut de format du contrôleur et déclenchent sa correction automatique ; elles ne nécessitent pas une nouvelle version du plan. Le moteur convertit seulement la réponse validée en lignes de couverture pour conserver le format durable historique. Les anciens FAIL issus de revues incomplètes restent visibles et reçoivent une rectification distincte.

## Correction éditoriale persistante et contrat26b.report.2

Le dernier refus éditorial de la tâche reste dans pending_report_correction, rafraîchi avant chaque inférence et avant la réduction du contexte. Un PASS technique ultérieur ou le PASS d’une autre tâche ne l’efface pas ; une nouvelle revue éditoriale PASS de la même portée le résout. Les constats sont bornés dans la vue du modèle et restent complets dans l’événement d’origine. report_correction_context_prepared permet d’observer leur préparation ; cet événement n’annonce pas à lui seul que le modèle a corrigé le texte.

Un test réel a révélé que le relecteur pouvait classer des affirmations historiques fausses comme non factuelles. Le contrat de rapport26b.report.2 refuse cette catégorie pour les formes explicites d’opération passée, de date d’opération et de comptage prises en charge ; il refuse aussi d’inventer une qualification hypothétique absente du texte. Le contrôleur doit se corriger avant que sa revue soit recevable. Son empreinte de contrat distincte invalide les anciens caches de prose sans modifier la couverture des plans. Ces garde-fous syntaxiques complètent le contrôle du modèle, sans prétendre reconnaître toutes les paraphrases factuelles possibles.

## Contrôle des sources citées et contexte borné — contrat26b.report.7

Les références event:N, event N et leurs listes sont résolues dans la mission d’origine, avec type, acteur, date réelle, résultat, contrat et contrôles lorsque disponibles. Chaque événement cité exige un contrôle distinct de soutien au texte ; le statut FAIL seul ne prouve pas une cause commune. Les événements d’une autre mission ne sont pas importés. Les contrats actifs sont fournis explicitement. Une approbation éditoriale n’est jamais une preuve indépendante d’un état technique et ne s’auto-valide pas.

Les essais ont utilisé des entrées de contrôle dépassant110000 caractères et produit des JSON incomplets ainsi que de fausses déclarations d’absence de références pourtant présentes. La cause interne de chaque sortie incomplète n’est pas établie. La vue du modèle est désormais sélectionnée : reçus explicitement cités, dernière observation des chemins mentionnés, quelques observations récentes, index complet des références, compteurs canoniques, sources des événements cités et seules définitions de tâches pertinentes. Les omissions sont signalées comme telles, jamais interprétées comme une absence. Le snapshot complet, la vue exacte et leurs empreintes restent durables. Un corpus cité qui excède encore le budget est INSUFFICIENT et ne publie rien. Le contrôle utilise temperature=0 et presence_penalty=0 ; les métriques d’inférence et tailles d’entrées sont conservées sans exposer le raisonnement interne.

Le contexte de travail recharge plans, tâches et couverture avant chaque inférence, y compris après une sauvegarde de plan dont la revue a échoué. mission_progress renvoie par défaut les métadonnées compactes et une vue de preuves bornée ; plan_version restitue la définition intégrale d’une version, courante ou historique. recheck_coverage=true relance l’audit du même candidat sans créer artificiellement une version supplémentaire. Les erreurs éditoriales restent visibles jusqu’à correction, même après un PASS technique.

Le premier retest de la vue bornée a dépassé le budget et a été refusé avant inférence. Le contrat26b.report.7 compresse donc davantage les métadonnées non citées et évite de fournir deux fois le texte du rapport ; les passages exacts suffisent. Les faits originaux des événements explicitement cités restent intacts. Ce refus technique est conservé, sans résultat positif inventé.

Les raisons du contrôle sont bornées (200 caractères par passage,160 par événement), les références principales limitées à6 par passage et les constats généraux à8. Chaque passage et chaque source explicitement citée restent obligatoires : raccourcir les justifications ne supprime aucun contrôle. Le budget de sortie augmente avec ces contrôles requis, jusqu’à16384 tokens. Le texte source complet est conservé. La liste exhaustive des identifiants autorisés reste imposée par le schéma sans être dupliquée dans les données ; les alias de références de mission, tâche, plan et contrat sont explicites.

Le contrat de couverture26b.9 exige également un ordre explicite entre tous les producteurs déclarés du même artefact : attendre plusieurs producteurs ne suffit pas si leurs propres écritures restent non ordonnées. Ce contrôle corrige le faux PASS observé sur le plan C/v7 ; le modèle choisit ses nouvelles dépendances ou réduit ses sorties redondantes, sans plan fourni par Codex.
